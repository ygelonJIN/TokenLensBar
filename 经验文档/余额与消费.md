# 余额与消费

**什么时候读**：接新平台余额、余额显示 0、消费金额对不上、要给某个 provider 加余额查询。

## 余额从哪来

**什么时候用**：第一次开余额，或某个平台查不出来。

默认不联网。`balances.json` 里 provider 的 `enabled` 为 `true` 才会发请求，Key 放 `secrets.json`（600 权限）。

三条路完全不同：

- **DeepSeek**：官方开放平台余额接口，Bearer 鉴权，Key 就是 `sk-` 推理 Key 本身。
  返回总额 / 赠送 / 充值三个分项，实际扣费优先扣赠送余额。
- **Xiaomi MiMo**：没有 API Key 余额接口，只能用控制台会话。
  `platform.xiaomimimo.com` 的 cookie 必须同时含 `serviceToken` 和 `userId`，
  两个都缺一不可；`tp-*` / `ttp-*` 这类 Token Plan 推理 Key 查不了余额。
  它更像控制台接口，不稳定且有安全风险，默认关闭。
- **OpenCode Go（订阅）**：没有余额 API（社区还在提 issue 要求暴露 credit balance），
  数据只在控制台的 JSON 接口里：`GET /console/api/go/status`，**必须带 `x-org-id` 请求头**，
  否则一律 400 `OrgRequired`。返回的 `access.meters` 里三个窗口是
  `fiveHour` / `week` / `month`，每个给 `limitMicroCents` 和 `usedMicroCents`，
  **1 美元 = 1e8 micro-cents**（6000000000 → $60）。剩余 = 上限 − 已用。

**坑**：MiMo 的 userId 在浏览器 Cookies 表里也能拿到，不用翻网络面板。

**坑**：新版控制台是 `/console/org_xxx`，而**所有 HTML 路由都返回同一个约 4545 字节
的 SPA 骨架**（`/console`、`/console/<org>/go`、`/billing` 全是这个），
所以抓 HTML 永远拿不到数字，别在这上面浪费时间。数据是页面 JS 打接口渲染的。

**坑**：`x-org-id` 的值来自 localStorage 的 `opencode-console.org-id`，但它**带双引号**
（`"org_01M6..."`），原样塞进请求头会被判成 `OrgRequired`，必须先剥引号。

**坑**：Go 订阅的余额是**订阅额度**，不是充值余额。$10 的档位对应 $12 / $30 / $60
三个窗口上限（接口确认过），所以面板上显示 $60 是"本月额度还剩多少"，
不是他付的钱。面板上的"今日消费"永远是 0，那是对的；订阅花销要看额度下降。

## OpenCode Go 额度

**什么时候用**：接了 OpenCode Go 订阅、要让它显示剩余额度、或一直显示"读取中"。

配置（`balances.json`）：

```json
{
  "id": "opencode-go",
  "type": "opencode",
  "name": "OpenCode Go 额度",
  "enabled": true,
  "secret": "opencode_cookie",
  "workspace_id": "",
  "window": "monthly",
  "mode": "go",
  "limits": { "rolling": 12, "weekly": 30, "monthly": 60 }
}
```

- `window`：`monthly` / `weekly` / `rolling`，决定余额栏显示哪个窗口的剩余额度。
  想看三个窗口就加三条 provider（`id` 不同），面板会排成三行。
- `workspace_id` 留空就自动探测：带 Cookie GET `/console`，从重定向或页面里认
  `org_` / `wrk_`。认不出来就手填。
- `mode`：`go` 读额度窗口（订阅），`zen` 读预付费余额。
- `limits` 只在接口没给金额时兜底（接口给了就以接口为准）。

### 取数顺序（四层，从稳到脆）

1. **API Key 直连（默认，最稳：不要浏览器、不要 Cookie、不要磁盘权限）**：
   `GET /console/api/go/status`，`Authorization: Bearer oc_sk_...`，直接回
   `access.meters`（micro-cents）。Key 来源优先级：`secrets.json` 的 `opencode_key`
   → 环境变量 `OPENCODE_GO_API_KEY` → DSH 的 `~/.dsh/.credentials.yaml`。
   **必须带浏览器 UA**，否则 Cloudflare 直接 1010 拦成 403。
   Bearer 鉴权**不需要** `x-org-id`；只有 Cookie 会话鉴权才需要。
2. **浏览器代查**：Safari/Chrome 里开着任意 `opencode.ai` 页面，用 `osascript`
   让标签页自己带 `x-org-id` 请求，只把 JSON 拿回来。依赖「自动化」+「允许 Apple
   事件中的 JavaScript」，浏览器关掉就不可用。
3. **磁盘 Cookie 直连**：`Cookies.binarycookies` 里的 `auth`（要磁盘访问权限有效）。
4. **手填 Cookie**：`secrets.json` 的 `opencode_cookie`。

接口 JSON 认不出来时依次退：老版 `/workspace/wrk_xxx` 页面的 SSR
（`rollingUsage` / `weeklyUsage` / `monthlyUsage` 的 `usagePercent`）→
页面渲染文字里的 `X% used`。三层都空才报错，报错里带 JSON 开头，方便对症。

`via_browser: false` 关掉代查，`auto_cookie: false` 关掉磁盘读取。

Cookie 兜底：

```
python3 tokenlensbar.py cookie --opencode --check          # 只体检，不写东西
python3 tokenlensbar.py cookie --opencode --from-clipboard # 剪贴板放好 auth=... 再跑
python3 tokenlensbar.py cookie --opencode --probe          # 探页面结构与存储
python3 tokenlensbar.py cookie --opencode --probe --json   # 打印接口原始 JSON
```

**坑**：读 Safari Cookie 要「系统设置 → 隐私与安全性 → 完全磁盘访问权限」，
授权对象是**真正去打开文件的二进制**，不是菜单栏 App。实测链条是
`TokenLensBar.app → /usr/bin/python3 → Xcode 里的 python3.9`，给 App 开的权限
传不到这一层；用 launchd 探针验证过，即使把 python3.9 加进完全磁盘访问权限，
launchd 里跑出来仍是 `PermissionError`。所以**别把这条路当默认**，走代查。

**坑**：AppleScript 的字符串里 `\` 只有 `\" \\ \n \r \t` 是合法转义，JS 里写
`\/` 会直接语法错（`-2741`）；`tell` 块里用局部变量会报「变量 r 没有定义」
（`-2753`）。所以内嵌 JS 一律不含引号和反斜杠，标签枚举用内联表达式。

**回退**：`enabled` 改 `false`，或 `auto_cookie: false` 只用 `secrets.json` 里手填的
`opencode_cookie`。余额样本留在 `usage.db`，不影响 token 统计。


## 缓存与刷新

**什么时候用**：改了余额却不更新，或面板卡在旧数字。

- 余额缓存 10 分钟（`refresh_seconds: 600`）；面板每 60 秒读缓存，不发网络请求。
- **谁刷余额**：只有菜单栏 App。launchd 那个每 5 分钟的采集任务跑的是
  `scan --no-balance`——它没有 Apple 事件和磁盘权限，让它刷只会写一堆失败、
  还占掉刷新窗口。别把 `--no-balance` 去掉，除非换了个有权限的执行上下文。
- 失败保留上一次的值，不清零——看到旧数字先看采集状态和更新时间。
- **面板提示**：MiMo / OpenCode 这类取不到数时，菜单栏那行不再显示整串报错，
  而是「已 N 小时没更新 · 下一步点哪里」；完整原因保留在 payload 的 `detail` 里。
  MiMo 存 Cookie 时会顺手记 `mimo_cookie_at`，用到 20 小时后会提前提醒
  「随时可能过期 · 粘一次更稳」。
- 想立刻刷：菜单栏面板「立即采集」，或 `python3 tokenlensbar.py balance --refresh`。

## MiMo Cookie 自动续期与手动兜底

**什么时候用**：MiMo 余额停在旧数字、报「Cookie 已失效」、换浏览器或重装后要重新配 Cookie。

MiMo 的 Cookie 是约一天寿命的短效会话，过期是常态，跟充值、重置都没关系。
浏览器一直保持着登录，是因为浏览器自己在悄悄续期；复制出来的那份是静态快照，
不会跟着续。过期后接口 401，余额按「失败保留旧值」停在最后一次成功的数字上，
看起来就是「怎么采集都不更新」。

### 浏览器代查（默认首选）

**什么时候用**：日常就靠它；Cookie 路线失败时它也是主力。

实测：新版 Safari 的会话 Cookie **只活在内存里**，`Cookies.binarycookies` 落盘不含它，
磁盘上拿不到（深度扫描 3000+ 文件验证过）。于是不取 Cookie，
用 `osascript` 让已登录的 Safari 标签页自己发 XHR 调余额接口，只拿结果。

- 前提三件：Safari 开着 `platform.xiaomimimo.com` 的标签页；Safari 设置 → 高级 →
  勾「显示网页开发者功能」，然后「开发」菜单 → 勾「允许 Apple 事件中的 JavaScript」；
  首次代查时系统弹「允许控制 Safari」点允许。
- 不碰 Cookie、不碰存储、不需要完全磁盘访问权限。
- 关掉：`balances.json` 里对应 provider 加 `"via_browser": false`。
- 取数顺序：浏览器代查 → Cookie 接口 → 自动换新 Cookie 重试 → 都失败保留旧值并记原因。

### Cookie 自动续期怎么工作

- 触发：MiMo 余额请求返回 401/403 时，自动从 Safari 的 Cookie 库读新的
  `api-platform_serviceToken` + `userId`，写回 `secrets.json`（600、原子替换、
  不打印值），再重试一次余额请求。只取 `xiaomimimo.com` 域的这两个字段。
- 解析全程自校验（页大小之和、偏移边界、字符串、日期区间都验），
  认不出的布局直接报错走手动，不会把乱数据写进 `secrets.json`。
- 权限前提：读 Safari Cookie 要「系统设置 → 隐私与安全性 → 完全磁盘访问权限」，
  授权给跑采集的程序（手动跑就是终端；launchd 跑看它以什么身份执行）。
  没权限就自动降级成手动，不会卡住采集。
- 关掉自动：`balances.json` 里对应 provider 加 `"auto_cookie": false`，回到纯手动。

### 手动兜底

- `python3 tokenlensbar.py cookie`：手动触发一次自动续期。
- `python3 tokenlensbar.py cookie --from-clipboard`：剪贴板里放好
  `api-platform_serviceToken=...; userId=...` 再跑，校验两个字段后写入。
- `python3 tokenlensbar.py cookie --check`：只读体检（配置、Safari 可读性、
  找到的字段名、上次成功时间），不改任何东西。自动失败先跑这个看原因。

**坑**：

- 值只存在 `secrets.json`，不进文档、日志、提交信息；错误信息里也只有原因没有值。
- 改密码、账号重置、在别处重新登录会立刻作废旧会话，一天没到也会提前失效。
- Safari 退出登录后自动续期会一直失败，先去浏览器重新登录控制台。
- Safari 没开控制台标签页时代查不了；不开浏览器代查就只剩 Cookie / 手动路线。

### 回退

自动续期不改余额语义：失败照样保留旧值、记错误，随时可只用 `--from-clipboard`。
不想让它碰浏览器：`auto_cookie: false`；不要 Cookie 功能：删掉 `secrets.json` 里的
`mimo_cookie` 或把 provider 的 `enabled` 改成 `false`，token 统计不受影响。

## 消费是余额差分，不是账单

**什么时候用**：核对「今日消费」跟官方账单对不上、历史/看板的金额怎么来的、或想手动补一笔。

三处共用一套算法，只是展示粒度不同：

| 位置 | 函数 / 字段 | 粒度 |
| --- | --- | --- |
| 概览「消费」 | `today_spend` → `today_spend` | 今天，单日 |
| 历史页签 | `spend_daily(days=None)` → `spend_history` | 全部历史 + 近 7 天 + 每天明细（面板列最近 7 天） |
| 看板 | `spend_daily(days=N)` → `spend` | 当前窗口 + 每天明细（表格列最近 31 天） |
| 命令行 | `report` 的「实付」行 | 报告的窗口 |

算法：

1. **起点**：当天第一条有效余额样本。早上 8 点开机、8 点第一条样本，就从 8 点开始算。
2. **金额**：相邻样本之间所有**余额下降**之和。
3. **充值 / 退款 / 赠送**：余额上涨直接忽略，不记、不显示。
4. **跨天缺口**：没有日志可归因的，静默忽略，不摊到任何一天（所以「每日实付」加起来
   可能小于余额实际下降）。
5. **升级当天**：还没有更早的样本，用 `balances` 表里最近一次余额补一条起点。
6. **窗口起点**：窗口第一天之前会多取一条样本当起点，否则第一天只剩当天内的下降，
   数值偏小。
7. **币种**：按 provider 余额的币种分桶，USD（如 OpenCode Go 额度）和 CNY 并排显示，
   不换汇、不相加。

手动补记（`balance --add`）是**额外项**，只补余额没覆盖到的消费，统一记到主币种
（`prices.currency`）。余额已经算过的不要再补，否则重复。

**坑**：今天这一格必须和概览的「消费」完全一致，两边都改了才算改对。`spend_daily`
的跨天归因靠事件列表，看板接口（`api_payload`）一度只传窗口内的事件，导致昨天的会话
拿不到、整段缺口被算进今天（$9.60 vs $9.71）；现在改成取全量事件再归因。

**回退**：这三处只是展示。不想看到就关掉对应 provider 的 `enabled`；`spend_daily`
不动余额样本、不改 `events`，删掉展示代码不影响采集。

## 为什么它不是账单

**什么时候用**：发现差额，判断要不要追。

- 服务商余额有延迟，临时冻结也会体现成下降。
- 同一个采样间隔里既充值又消费，只能看到净值，可能少算。
- 余额法按天粒度，没有逐请求归因；Token 估算才是按请求算的，两者口径不同。
- 订阅类平台（OpenCode Go）的「消费」其实是额度消耗，不是真扣钱，看额度下降即可。
- 所以：**消费看趋势，跟官方账单对账用余额分项 + 充值记录。**

## 加一个 provider 要改哪几处

**什么时候用**：Kimi、OpenRouter 这类也是 Bearer 余额接口的平台。

1. `balances.json` 加一条 provider（`id` / `type` / `name` / `enabled`）。
2. `secrets.json` 加对应 Key，`chmod 600`。
3. `tokenlensbar.py` 里照 `fetch_deepseek_balance` 写一个 `fetch_<平台>_balance`，约 30 行，
   处理返回结构差异和非 200。
4. `tests/test_balance.py` 补一组：正常、401、超时、结构异常。

**坑**：Key 只写进 `secrets.json`，不出现在日志、命令行参数和报错里。

## 回退

**什么时候用**：余额配置改坏了，想回到不联网的状态。

把 `balances.json` 里对应 provider 的 `enabled` 改成 `false`，或直接删掉 `balances.json`——
之后就完全不发请求。余额样本留在 `usage.db` 里，不影响历史 token 统计。
