# 余额与消费

**什么时候读**：接新平台余额、余额显示 0、消费金额对不上、要给某个 provider 加余额查询。

## 余额从哪来

**什么时候用**：第一次开余额，或某个平台查不出来。

默认不联网。`balances.json` 里 provider 的 `enabled` 为 `true` 才会发请求，Key 放 `secrets.json`（600 权限）。

两条路完全不同：

- **DeepSeek**：官方开放平台余额接口，Bearer 鉴权，Key 就是 `sk-` 推理 Key 本身。
  返回总额 / 赠送 / 充值三个分项，实际扣费优先扣赠送余额。
- **Xiaomi MiMo**：没有 API Key 余额接口，只能用控制台会话。
  `platform.xiaomimimo.com` 的 cookie 必须同时含 `serviceToken` 和 `userId`，
  两个都缺一不可；`tp-*` / `ttp-*` 这类 Token Plan 推理 Key 查不了余额。
  它更像控制台接口，不稳定且有安全风险，默认关闭。

**坑**：MiMo 的 userId 在浏览器 Cookies 表里也能拿到，不用翻网络面板。

## 缓存与刷新

**什么时候用**：改了余额却不更新，或面板卡在旧数字。

- 余额缓存 10 分钟（`refresh_seconds: 600`）；面板每 60 秒读缓存，不发网络请求。
- 缓存过期后由采集器在扫描时顺带刷新，面板不会因为网络卡住。
- 失败保留上一次的值，不清零——看到旧数字先看采集状态和更新时间。
- 想立刻刷：菜单栏面板「立即采集」，或 `python3 tokenlensbar.py balance --refresh`。

## MiMo Cookie 自动续期与手动兜底

**什么时候用**：MiMo 余额停在旧数字、报「Cookie 已失效」、换浏览器或重装后要重新配 Cookie。

MiMo 的 Cookie 是约一天寿命的短效会话，过期是常态，跟充值、重置都没关系。
浏览器一直保持着登录，是因为浏览器自己在悄悄续期；复制出来的那份是静态快照，
不会跟着续。过期后接口 401，余额按「失败保留旧值」停在最后一次成功的数字上，
看起来就是「怎么采集都不更新」。

### 浏览器代查（默认首选）

**什么时候用**：日常就靠它；Cookie 路线失败时它也是主力。

实测：新版 Safari 的会话 Cookie **只活在内存里**，`Cookies.binarycookies` 落盘不含它，
磁盘上拿不到（深度扫描 3000+ 文件验证过）。于是不取 Cookie，
用 `osascript` 让已登录的 Safari 标签页自己发 XHR 调余额接口，只拿结果。

- 前提三件：Safari 开着 `platform.xiaomimimo.com` 的标签页；Safari 设置 → 高级 →
  勾「显示网页开发者功能」，然后「开发」菜单 → 勾「允许 Apple 事件中的 JavaScript」；
  首次代查时系统弹「允许控制 Safari」点允许。
- 不碰 Cookie、不碰存储、不需要完全磁盘访问权限。
- 关掉：`balances.json` 里对应 provider 加 `"via_browser": false`。
- 取数顺序：浏览器代查 → Cookie 接口 → 自动换新 Cookie 重试 → 都失败保留旧值并记原因。

### Cookie 自动续期怎么工作

- 触发：MiMo 余额请求返回 401/403 时，自动从 Safari 的 Cookie 库读新的
  `api-platform_serviceToken` + `userId`，写回 `secrets.json`（600、原子替换、
  不打印值），再重试一次余额请求。只取 `xiaomimimo.com` 域的这两个字段。
- 解析全程自校验（页大小之和、偏移边界、字符串、日期区间都验），
  认不出的布局直接报错走手动，不会把乱数据写进 `secrets.json`。
- 权限前提：读 Safari Cookie 要「系统设置 → 隐私与安全性 → 完全磁盘访问权限」，
  授权给跑采集的程序（手动跑就是终端；launchd 跑看它以什么身份执行）。
  没权限就自动降级成手动，不会卡住采集。
- 关掉自动：`balances.json` 里对应 provider 加 `"auto_cookie": false`，回到纯手动。

### 手动兜底

- `python3 tokenlensbar.py cookie`：手动触发一次自动续期。
- `python3 tokenlensbar.py cookie --from-clipboard`：剪贴板里放好
  `api-platform_serviceToken=...; userId=...` 再跑，校验两个字段后写入。
- `python3 tokenlensbar.py cookie --check`：只读体检（配置、Safari 可读性、
  找到的字段名、上次成功时间），不改任何东西。自动失败先跑这个看原因。

**坑**：

- 值只存在 `secrets.json`，不进文档、日志、提交信息；错误信息里也只有原因没有值。
- 改密码、账号重置、在别处重新登录会立刻作废旧会话，一天没到也会提前失效。
- Safari 退出登录后自动续期会一直失败，先去浏览器重新登录控制台。
- Safari 没开控制台标签页时代查不了；不开浏览器代查就只剩 Cookie / 手动路线。

### 回退

自动续期不改余额语义：失败照样保留旧值、记错误，随时可只用 `--from-clipboard`。
不想让它碰浏览器：`auto_cookie: false`；不要 Cookie 功能：删掉 `secrets.json` 里的
`mimo_cookie` 或把 provider 的 `enabled` 改成 `false`，token 统计不受影响。

## 消费是余额差分，不是账单

**什么时候用**：核对「今日消费」跟官方账单对不上，或想手动补一笔。

算法（`balance --today`）：

1. **起点**：当天第一条有效余额样本。早上 8 点开机、8 点第一条样本，就从 8 点开始算。
2. **金额**：相邻样本之间所有**余额下降**之和。
3. **充值 / 退款 / 赠送**：余额上涨直接忽略，不记、不显示。
4. **跨天缺口**：没有日志可归因的，静默忽略，不摊到任何一天。
5. **升级当天**：还没有更早的样本，用 `balances` 表里最近一次余额补一条起点。

手动补记（`balance --add`）是**额外项**，只补余额没覆盖到的消费。
余额已经算过的不要再补，否则重复。

## 为什么它不是账单

**什么时候用**：发现差额，判断要不要追。

- 服务商余额有延迟，临时冻结也会体现成下降。
- 同一个采样间隔里既充值又消费，只能看到净值，可能少算。
- 余额法按天粒度，没有逐请求归因；历史页的 token 估算才是按请求算的，两者口径不同。
- 所以：**面板的「消费」看趋势，跟官方账单对账用余额分项 + 充值记录。**

## 加一个 provider 要改哪几处

**什么时候用**：Kimi、OpenRouter 这类也是 Bearer 余额接口的平台。

1. `balances.json` 加一条 provider（`id` / `type` / `name` / `enabled`）。
2. `secrets.json` 加对应 Key，`chmod 600`。
3. `tokenlensbar.py` 里照 `fetch_deepseek_balance` 写一个 `fetch_<平台>_balance`，约 30 行，
   处理返回结构差异和非 200。
4. `tests/test_balance.py` 补一组：正常、401、超时、结构异常。

**坑**：Key 只写进 `secrets.json`，不出现在日志、命令行参数和报错里。

## 回退

**什么时候用**：余额配置改坏了，想回到不联网的状态。

把 `balances.json` 里对应 provider 的 `enabled` 改成 `false`，或直接删掉 `balances.json`——
之后就完全不发请求。余额样本留在 `usage.db` 里，不影响历史 token 统计。
